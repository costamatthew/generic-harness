# 1B Tarefa e estado

> Trilha 1B da [Etapa 1](../plano-de-construcao.md#4-etapa-1-loop-mínimo-verificável-m0a). Componentes S2, M1 e M2 (HG §3.2). Data: 01/11/2026. Status: **aprovada** em 01/11/2026 (revisão delegada pela pessoa à janela principal do `/etapa 1`).
> Branch `etapa-1/1B`, worker 1, **depois da 1A** (plano §4, ondas). Começa no stub do gate e troca pela 1A assim que ela for mergeada na branch da etapa.
> **Pré-requisito:** o CI da Etapa 0 verde (ver [1A](1A.md)).

## Escopo

`task done`, `task block`, `task status` e `state`, que são os únicos escritores de `tasks.json`, do bloco de evidência de `validation.md` e dos blocos gerenciados do `STATE.md` (ADR-0003). Inclui o journal que garante que uma interrupção não produz uma conclusão sem prova (HG §3.7, "Estado e retomada").

**Dentro:**

1. **`task done <ID>`**, nesta ordem:
   1. reconcilia os journals pendentes (item 5);
   2. a task está `todo` ou `in-progress`. Se está `done` → `refused` (4), "já concluída em <runId>"; se está `blocked` → `refused`, "remova o blocker antes";
   3. pega `evidence.latest()` e aplica `evidence.check()` (API da 1A). `sensor-absent` → exit **3**, repetindo o `absent.reason` do manifesto; nenhum manifesto, `not-pass` ou `stale-*`/`*-tampered` → exit **4**, com `→ rode harness gate <ID>`. **O `task done` não roda o gate.** A [cli.md](../../contracts/cli.md#subcomandos) diz "aceita só um manifesto `pass` com `inputs.tree` igual à árvore atual", e o exit 4 existe para o verde antigo. O plano §4 diz "roda o gate": a divergência está registrada nas decisões em aberto;
   4. se a task tem `dod.checks`, confere a seção **Verifier** dessa task em `validation.md` (formato da [1D](1D.md#formato-da-seção-verifier)): a linha `tree:` é igual aos 7 primeiros caracteres de `inputs.tree`, cada check tem uma linha, e toda linha diz `atende` com evidência `arquivo:linha` ou `exec: <comando> exit=0`. Se faltar alguma coisa → exit 4, apontando a linha que falta. É o S7 ("check sem evidência = não atendido") cobrado por código;
   5. grava o journal, depois `tasks.json` (`status: done`, `evidence` com `runId`, `attempt`, `manifest`, `manifestSha256`, `tree`, `updatedAt`, `revision + 1`), depois o bloco de evidência em `validation.md`, depois o bloco de tasks do STATE, e por fim marca o journal como completo;
   6. a saída sugere o commit atômico, sem executá-lo: `→ git add <arquivos> && git commit -m "<ID>: <título>"`, com os arquivos tirados do `git status`. Commit é decisão da pessoa ou do agente, não do harness.
2. **`task block <ID> --reason <r> [--needs <n>]`**: `status: blocked` + `blocker {reason, at, needs}` em `tasks.json` e uma linha na seção Blockers do STATE (`- <ID> <data>: <r> (precisa: <n>)`). Libera o Stop gate. Em task `done` → `refused`.
3. **`task status [ID]`**: tabela `ID · status · último gate (result, tree, attempt) · blocker`. `data.tasks` = lista com esses campos. Reconcilia antes, como todo subcomando `task`.
4. **`state [--handoff <texto>]`**: sem argumento, imprime o handoff, os blockers abertos e as tasks em andamento. Com `--handoff`, substitui o bloco `<!-- harness:begin handoff -->…<!-- harness:end handoff -->` por `<data UTC> · <texto>`. Se o STATE.md não existe, cria a partir de `core/templates/STATE.md` (1D).
5. **Journal e reconciliação.** `.harness/work/<W>/.journal/<runId>.json` = `{taskId, runId, manifestSha256, steps: {tasks, validation, state}, complete}`. Na reconciliação, para cada journal incompleto:
   - se `tasks.json` já está `done` com esse `runId`, conclui os passos que faltam. `validation` e `state` são idempotentes por `runId`: um marcador `run=<runId>` no bloco impede duplicar;
   - se não está, roda `evidence.check` de novo: `fresh` → conclui tudo; qualquer outro código → descarta o journal, a task fica como estava, e o resumo diz `→ a conclusão de <ID> foi interrompida e a árvore mudou; rode harness gate <ID>`.
6. **Concorrência e atomicidade.** Toda escrita usa `fsx.write_atomic`. O `revision` lido no início precisa ser igual ao do disco no momento de gravar; se não for → `refused` (4), "tasks.json mudou durante a operação". Lock por work item em `.harness/work/<W>/.journal/lock`.
7. **Pontos de falha para teste.** Com `HARNESS_TEST_CRASH_AT=<passo>` (`after-journal`, `after-tasks`, `after-validation`), o processo chama `os._exit(99)` depois do passo. A variável só tem efeito nesses três pontos e fica documentada aqui porque a 1G depende dela.

**Fora:** `task freeze` (3A, continua `not-implemented`); criação de `tasks.json` (na Etapa 1, a pessoa escreve à mão e confere com `harness validate tasks`; na Etapa 4, a 4S gera); a transição `todo → in-progress` (ver decisões em aberto); commit automático.

**`data` por subcomando:** `task done` → `{task, manifest, runId, tree}`; `task block` → `{task}`; `task status` → `{tasks}`; `state` → `{handoff, blockers}`.

## Critério binário da trilha

- [ ] `pytest` verde.
- [ ] Todo `tasks.json` gravado nos testes passa por `schema.validate(..., "tasks")`; uma task `done` sempre tem `evidence`, e uma `blocked` sempre tem `blocker`.
- [ ] Manifesto `pass` fresco + seção Verifier completa → exit 0. As três escritas acontecem, e `revision` sobe exatamente 1.
- [ ] Manifesto `pass` + uma edição num arquivo rastreado → exit 4, e `tasks.json` fica byte a byte igual.
- [ ] Manifesto `sensor-absent` → exit 3; manifesto `fail` → exit 4.
- [ ] Seção Verifier ausente, com `tree` diferente, com um check sem linha, com `não atende` ou com evidência sem `arquivo:linha` → exit 4 (um teste para cada caso).
- [ ] Para cada `HARNESS_TEST_CRASH_AT`: depois do crash, `task status` deixa a task `done` com evidência completa (validation + state, cada um uma vez só) **ou** não `done`. Nunca `done` sem evidência. Rodar `task done` de novo não duplica o bloco.
- [ ] Crash em `after-journal` + edição da árvore antes da reconciliação → a task não fica `done`, e o resumo pede o gate.
- [ ] `revision` divergente → exit 4, sem escrita.
- [ ] `state --handoff` duas vezes com o mesmo texto não muda o arquivo além da data; o conteúdo fora dos blocos é preservado byte a byte.
- [ ] Depois do merge da 1A: os testes rodam com o `run_gate` real, e não sobra import de `tests.stubs.gate_stub` em `tests/unit/task/`.

## O que usa de stub

- **[tests/stubs/gate_stub.py](../../../tests/stubs/gate_stub.py)** até a 1A entrar: `make_manifest(..., tree=<hash>)` gera manifestos `pass`, `fail`, `sensor-absent` e `error`.
- Enquanto `core.lib.tree` e `core.lib.evidence` não existem, os testes usam um `evidence_check` falso, injetado por parâmetro (`task_done(root, id, check=...)`). O código de produção importa a API da 1A. A troca é uma linha, e o último item do critério cobra.
- `core/templates/STATE.md` e o formato do Verifier vêm da 1D. Até o merge, os testes usam uma cópia mínima em `tests/unit/task/data/`.

## Decisões em aberto

1. **`task done` roda o gate ou só aceita um manifesto fresco?** Esta spec segue a [cli.md](../../contracts/cli.md) e o exit 4: só aceita. O plano §4 e o HG S2 dizem "roda o gate". Trocar custa pouco: o `run_gate` da 1A já pode ser chamado no mesmo processo. Mas aí o exit 4 por verde antigo deixa de ser observável no `task done`.
2. **Quem leva uma task para `in-progress`?** Não há subcomando para isso em `COMMANDS`, e o Stop gate só olha tasks `in-progress`. Proposta: na Etapa 1, a pessoa escreve `in-progress` no `tasks.json` manual da 1I. Alternativa: registrar **CC-001 `task start <ID>`** em `contract-changes.md` (trilha 1B).

**Decisão (01/11/2026, delegada pela pessoa à janela principal):** 1 → só aceita manifesto fresco, como na `cli.md` (o exit 4 de verde antigo é critério da 1I). 2 → sem CC-001; na Etapa 1 o `in-progress` é escrito à mão no `tasks.json` da 1I.
