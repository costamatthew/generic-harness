> **Pré-requisito:** o item "CI verde nos três SOs" da [Etapa 0](../etapa-0/spec.md#critério-de-saída) ainda está aberto. A implementação começa depois dele (plano §2.2); esta spec pode ser escrita antes.

## Escopo

`harness gate <ID>` lê a DoD da task em `tasks.json`, roda os comandos do perfil, lê o JUnit e grava um manifesto por tentativa, associado ao hash da árvore de trabalho. Também publica, em `core/lib/`, as funções de leitura e de frescor da evidência que a 1B e a 1C consomem.

**Dentro:**

1. **Localizar a task.** `T5` ou `PAG-12.T5`. Com `T5` puro, procura em `.harness/work/*/tasks.json`: zero ocorrências → `usage` (2); mais de uma → `usage`, listando os IDs qualificados.
2. **Resolver os comandos** de `dod.commands` no `profile.json` (`test.unit` → `commands.test.unit`; `lint` → `commands.lint`). Antes de rodar qualquer comando, confere todos:
   - nome ausente no perfil → check `absent`, `reason: not-in-profile`;
   - `status: planned` → `absent`, `reason: planned` (com `decidedBy` quando `origin` é `decision:ADR-NNNN`);
   - `status: detected | confirmed` → `absent`, `reason: not-approved` (o schema diz que só `verified` alimenta o gate);
   - se algum check ficou `absent`, nenhum comando roda: os outros viram `skipped`, e o resultado é `sensor-absent` (exit 3). Isso dá o GF §4.2 sem execução parcial.
3. **Rodar** cada comando com `shell=True`, no `cwd` do perfil (padrão: a raiz), com `timeoutSec` (padrão 600). stdout e stderr vão juntos para `.harness/runs/<runId>/<check>.log`. Se o shell responder 127, ou se o executável não existir, o check fica `unavailable` (`tool-missing`) e o resultado é `sensor-absent`. Em timeout, o check fica `fail`, com `exitCode: null` e a linha `timeout <n>s` no resumo.
4. **Ler o JUnit** (`core/lib/junit.py`) quando o comando declara `report` + `reportFormat: junit`:
   - aceita `<testsuites>` e `<testsuite>` na raiz, inclusive aninhados, e soma `tests`/`failures`/`errors`/`skipped`;
   - **relatório ausente ou com mtime anterior ao início da tentativa → `fail`**, mesmo com exit 0 (HG §3.7: relatório ausente ou reutilizado bloqueia o aceite). Grava `mtimeAfterStart`;
   - exit 0 com `failures + errors > 0` → `fail`;
   - copia o relatório para `.harness/runs/<runId>/<check>.junit.xml` e registra o caminho e o sha256 da **cópia**, porque o caminho do perfil é sobrescrito a cada run;
   - `firstFailures` (≤ 10) como `arquivo:linha`: atributos `file`/`line` do `<testcase>`; se não houver, o último `caminho:linha` do texto do `<failure>`/`<error>` que exista no repo; se nem isso, `classname` convertido em caminho, sem linha.
5. **Hash da árvore** `sha256-worktree-v0` (`core/lib/tree.py`). O algoritmo fica fixado aqui:
   - arquivos = `git ls-files -z --cached --others --exclude-standard`, menos os que casam com `treeExcludes` (glob com `**`, sempre com `/`);
   - para cada caminho, em ordem de bytes UTF-8: `caminho \0 tipo \0 sha256(conteúdo) \n`, com `tipo` ∈ `f` (arquivo), `x` (executável), `l` (symlink: o hash é do alvo do link, não do conteúdo) e `d` (rastreado, mas apagado na árvore: o hash é vazio);
   - `tree` = sha256 dessa sequência. Os bytes são lidos como estão, sem normalizar fim de linha;
   - `treeExcludes` padrão: `.harness/runs/**`, `.harness/work/*/tasks.json`, `.harness/work/*/validation.md`, `.harness/work/*/.journal/**`, `.harness/STATE.md`. São os arquivos que o próprio harness escreve depois do gate (1B) e o bloco do verifier (1D). Sem essa exclusão, `task done` invalidaria o próprio verde;
   - `revision` = `git rev-parse HEAD`, ou `null` sem commits; `dirty` = `git status --porcelain` não vazio, desconsiderando os excludes;
   - fora de um repo git → `usage`, com "o gate exige git; rode `git init`".
6. **Manifesto** em `.harness/runs/<runId>/manifest.json`, válido contra `run-manifest`, gravado de forma atômica. `attempt` = número de manifestos anteriores da task + 1; `supersedes` = o `runId` anterior; `profileSha256` = sha256 dos bytes de `.harness/profile.json`; `harnessVersion` vem de `core/lib/version.py`.
7. **Concorrência.** Um lock por task (`.harness/runs/<taskId>.lock`, `O_CREAT|O_EXCL`). Um segundo gate da mesma task responde `refused` (4). Lock com mais de `timeoutSec × checks` é tratado como órfão e removido com aviso.
8. **Saída** no formato de [cli.md](../../contracts/cli.md#saída-enxuta-padrão): uma linha `GATE` por check, contagens, `firstFailures`, `log:` e uma linha `→` para o agente (P15). `data` = `{ "manifest", "runId", "result", "tree" }`.
9. **`--prove-sensor`** → `not-implemented` (exit 10), citando a trilha 2E. O argumento já existe em `COMMANDS`.

**API interna para a 1B e a 1C** (não é contrato do §2.3, mas a 1B e a 1C programam contra ela; mudar a assinatura depois do merge exige avisar as duas):

| Função | Devolve |
| --- | --- |
| `core.lib.profile.load(root) -> dict` | o perfil validado; `ValueError` com os erros do schema |
| `core.lib.work.find_task(root, task_id) -> TaskRef` | `work_dir`, `doc` (o tasks.json), `task`; `LookupError` se não achar ou se for ambíguo |
| `core.lib.tree.compute(root, excludes=DEFAULT_EXCLUDES) -> str` | hex de 64 caracteres |
| `core.lib.evidence.latest(root, task_id) -> Path \| None` | o manifesto de maior `attempt` |
| `core.lib.evidence.check(root, manifest_path) -> Verdict` | `ok: bool`, `code`, `reason`. `code` ∈ `fresh`, `not-pass`, `sensor-absent`, `stale-tree`, `stale-profile`, `log-tampered`, `report-tampered`, `invalid-manifest` |
| `core.lib.fsx.write_atomic(path, text)` | temporário no mesmo diretório + `os.replace` |
| `core.cli.gate.run_gate(root, task_id) -> tuple[Result, Path \| None]` | o mesmo que o subcomando, chamável no próprio processo |

`evidence.check` só devolve `fresh` quando o manifesto é válido, `result == pass`, `inputs.tree` é igual a `tree.compute()` agora, `profileSha256` é igual ao do perfil atual e os sha256 de cada log e de cada relatório conferem.

**Fora:** test guard, baselines e `testsSha256` (3A); `--prove-sensor` (2E); assinatura do manifesto (ADR-0003, limite declarado); detecção de comandos (2B).

## Critério binário da trilha

- [ ] `pytest` verde, incluindo `test_stdlib_only` (ADR-0004).
- [ ] Todo manifesto que o gate grava nos testes passa por `schema.validate(..., "run-manifest")`.
- [ ] Sem nenhuma mudança na árvore, o hash é o mesmo em duas chamadas. Muda quando: um arquivo rastreado é editado sem commit, um não rastreado e não ignorado é criado, um rastreado é apagado ou o bit de execução muda. **Não** muda quando: um arquivo ignorado ou um caminho dos `treeExcludes` é escrito.
- [ ] Exit 0 com JUnit de 1 falha → `fail`, com `firstFailures[0].location` no formato `arquivo:linha`, tanto em xunit1 quanto em xunit2.
- [ ] Exit 0 com relatório ausente ou anterior ao início → `fail`.
- [ ] Comando `planned`, `confirmed` ou ausente no perfil → exit 3, manifesto `sensor-absent`, nenhum comando executado (provado com um comando que criaria um arquivo).
- [ ] `evidence.check` devolve cada um dos 8 códigos num teste próprio; editar um log ou relatório depois do gate dá `*-tampered`; editar o perfil dá `stale-profile`.
- [ ] Dois gates concorrentes da mesma task: um roda, o outro sai com 4.
- [ ] A saída sem `--json` tem no máximo `limits.summaryLines` linhas, e a primeira segue `GATE <ID> <check>  <PASS|FAIL|ABSENT> exit=<n>  <dur>s  tree=<7 hex>`.
- [ ] Os testes rodam no Windows: caminhos com `/` no manifesto e o bit `x` ignorado onde o SO não o tem (o CI da matriz cobra).

## O que usa de stub

Nenhum: a 1A é a primeira da cadeia. Consome os schemas `profile`, `tasks`, `run-manifest` e `cli-output` e os exemplos em `core/schemas/examples/`. Os repos de teste são criados por `git init` em `tmp_path`, porque o repo-fixture da 1G ainda não existe quando a 1A começa.

## Pontos de atenção

- **O pytest padrão (xunit2) não grava `file`/`line`** no `<testcase>`. Por isso existe o fallback do item 4. No piloto midcortes, o perfil manual usa `-o junit_family=xunit1` (ver a 1G).
- **Windows:** sem bit de execução e com `\` nos caminhos que o git devolve com `core.quotepath`. Use `-z` e decodifique em UTF-8.
- `git ls-files --others` em repo grande pode ser lento. O hash roda também no Stop hook (1C): meça no midcortes na 1I e registre o tempo.
